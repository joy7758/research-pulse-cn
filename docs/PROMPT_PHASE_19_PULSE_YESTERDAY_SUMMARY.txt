Implement Phase 19 only: pulse yesterday-summary card v1.

Hard boundaries for this phase:
- Do not implement any external web/news/paper retrieval.
- Do not implement related-paper or related-news recommendation fetching.
- Do not add AI summarization, AI query generation, or LLM-based recap text.
- Do not add new delivery channels.
- Do not add customer-facing UI beyond minimal compatibility needed for existing desktop/digest views.
- Do not sync local file contents, note contents, or review-note contents to the backend.
- Do not add multi-tenant or institution features.
- Do not weaken existing admin auth, internal service auth, device-token sync auth, mini-read auth, or official-account provider boundaries.
- Do not replace the modular monolith backend architecture.

Primary goal:
Add a deterministic "yesterday summary" pulse card using only WorkActivityEvent data.

This phase should make the repository suitable for:
- generating one concise previous-day work summary card per user per pulse run
- previewing yesterday-summary input and scoring inside the existing pulse pipeline
- persisting yesterday-summary cards into PulseCard when selected
- including yesterday-summary cards in digest/today views without external retrieval

Architectural intent:
- Yesterday summary is generated from WorkActivityEvent only.
- No AI or external retrieval is involved.
- It should fit the existing facts -> candidates -> scoring -> suppression -> selection pipeline.
- It should remain explainable and deterministic.

Required changes:

1. Extend pulse card model
Add support for a new card type:
- yesterday_summary

Requirements:
- update enums / schemas / validators / API response models as needed
- keep schema changes minimal
- if a database migration is required for enum evolution, add the minimal Alembic migration
- source_paper_id may remain null for this card type
- candidate_metadata and score_breakdown should carry enough explanation for ops/debugging

2. Yesterday summary builder service
Add a deterministic service for building a previous-local-day work summary from WorkActivityEvent rows.

Requirements:
- input:
  - user_id
  - target local date or effective timezone context
- default target should be the previous local date relative to the effective pulse timezone
- effective timezone resolution order:
  1. explicit request parameter if provided
  2. first enabled daily SubscriptionPolicy policy.timezone if available
  3. app default timezone
- include only user-work-centric activity
- exclude source=system events from the summary
- output must be machine-readable and include at minimum:
  - summary_date
  - total_events
  - activity_type_counts
  - touched_papers with paper_id/title/activity_count
  - distinct_activity_type_count
  - top_activity_types
- add a deterministic short text summary builder from this structure
- no AI generation

3. Pulse fact/candidate generation
Integrate yesterday summary into the existing pulse pipeline.

Requirements:
- generate at most one yesterday_summary candidate per user per pulse run
- do not generate a candidate when total_events = 0
- candidate title/summary/why_now must be deterministic and concise
- candidate_metadata should include:
  - summary_date
  - total_events
  - activity_type_counts
  - touched_paper_ids
  - touched_paper_titles when practical
- maintain compatibility with existing preview payloads

4. Scoring and ordering
Integrate yesterday_summary into scoring and tie-break logic.

Requirements:
- add configurable scoring knobs, at minimum:
  - yesterday_summary_base_weight
  - yesterday_summary_min_events default 1
  - yesterday_summary_activity_diversity_bonus
  - yesterday_summary_multi_paper_bonus
- scoring should be deterministic and explainable
- score modifiers may depend on:
  - total_events
  - distinct activity types
  - number of touched papers
- update card_type ordering to include yesterday_summary in a documented stable place
- do not let this break existing tie-break determinism

5. Suppression and dedupe
Add safe suppression behavior for yesterday_summary.

Requirements:
- yesterday_summary should respect existing:
  - quiet hours
  - frequency cap
  - low-score suppression
- dedupe should prevent repeating the same yesterday summary for the same:
  - user
  - summary_date
  - card_type = yesterday_summary
within the existing dedupe logic/window or a minimal explicit extension if needed
- no fake duplicate generation

6. Pulse preview and run behavior
Enhance existing endpoints:

A. POST /pulse/preview/{user_id}
Requirements:
- include yesterday_summary candidate when applicable
- include its score breakdown and suppression reasons if suppressed
- include enough metadata to inspect the summary_date and event counts

B. POST /pulse/run/{user_id}
Requirements:
- if yesterday_summary is selected, persist it as a PulseCard
- ensure existing outbox/delivery flow remains intact
- summary_date should remain inspectable from PulseCard candidate_metadata/build fields

Update downstream consumers minimally so they tolerate yesterday_summary cleanly.

Requirements:

Logging requirements:
