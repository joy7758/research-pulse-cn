# MVP Interface Principles v1

## 目标

本文件定义 China-first Research Pulse MVP 的交互原则。

它解决的不是“页面长什么样”，而是“页面应该如何帮助中国科研用户更少思考界面、更多推进研究”。

## 产品铁律

> 我们多做一百步，客户少走一步。

落到界面上的含义是：

- 系统先理解和整理
- 用户主要做确认、选择、推进
- 不把底层复杂性直接暴露给用户

## 核心原则

### 1. 首页不做文献库，只做今日 Pulse

首页不是论文数据库入口，而是今日工作起点。

首页必须优先回答：

1. 今天该看什么？
2. 哪些论文需要处理？
3. 下一步该做什么？

### 2. 每页一个主动作

每个页面只保留一个最重要的主按钮或主任务。

示例：

- 首页：`生成今日 Pulse` 或 `刷新今日 Pulse`
- 导入页：`确认导入`
- 论文进度页：`更新进度`
- 公众号草稿页：`复制草稿`
- 小程序预览页：`复制 path` 或 `查看 payload`

### 3. 默认由系统自动处理

系统应优先自动完成：

- 导入格式识别
- 字段归一化
- 可提交记录判断
- 重复提示
- 元数据待补全识别
- Pulse 草稿生成
- 多端草稿 payload 转换

用户不应先配置规则，除非默认策略确实不够用。

### 4. 用户只处理例外和决策

用户的操作应尽量压缩为：

- 确认导入
- 选择重点论文
- 更新阅读状态
- 写下一步动作
- 处理少量异常记录

而不是手工管理所有细节。

### 5. 错误必须翻译成建议

不要只显示技术失败或字段缺失，要显示可操作的中文建议。

示例：

- 不好：`Validation error`
- 更好：`这条记录缺少题名，暂时无法导入`
- 更好：`该记录缺少年份，仍可导入，建议后续补全`

### 6. 用户不需要理解底层格式

界面上尽量避免让用户直接面对：

- CSL JSON
- BibTeX
- RIS
- CSV / TSV 差异
- raw payload

用户看到的应该是：

- 已识别 12 条论文
- 9 条可导入
- 2 条建议补全年份
- 1 条缺少题名，暂不可导入

### 7. 术语必须贴近中国科研语境

优先使用：

- 待读
- 略读中
- 精读中
- 已读
- 待补全
- 待筛选
- 下一步动作
- 今日重点论文

谨慎暴露底层技术词：

- parser
- payload
- preview token
- normalized record

这些词只保留在开发文档和接口层。

### 8. `draft / preview / not_sent` 必须显式可见

所有输出到渠道的内容都必须明确说明状态，避免用户误判为已经发送或已经发布。

必须明确标识：

- 公众号摘要：`草稿` / `未发送`
- 桌面通知：`草稿`
- 小程序详情：`预览`

禁止使用：

- 已发送成功
- 已推送成功
- 已发布

除非未来真的发生了真实投递并有可验证回执。

### 9. 复杂功能下沉到二级界面

首页只保留最必要的信息和入口。

复杂信息放到：

- 右侧详情面板
- 展开区
- 二级页面

例如：

- 题录字段细节
- 元数据缺失原因
- payload preview
- share-safe redaction 说明

### 10. 系统应尽量先分组，而不是让用户先整理

系统默认把论文放进更容易理解的工作视角：

- 待读
- 精读中
- 高优先级
- 有下一步动作
- 待补全
- 新导入待筛选

而不是要求用户先建 collection / folder / tag 体系。

## 页面级原则

## 首页：今日 Research Pulse

- 第一屏必须直接给出结构化结论
- 允许一个自然语言输入框作为高级入口
- 不以论文总库列表作为首页主视图

## 导入页

- 只保留三步：
  - 拖入或粘贴
  - 系统自动预览
  - 用户确认导入
- 不做复杂导入配置中心

## 论文进度页

- 页面名称优先叫“论文进度”，而不是“论文管理”
- 默认按工作状态看论文，而不是按数据库表格看论文

## 公众号草稿页

- 强调内容草稿和复制导出
- 不暴露真实发送能力

## 桌面通知页

- 强调短文本提醒与 deep link 占位
- 不伪装成真实系统通知中心

## 小程序详情预览页

- 强调 payload、path、share-safe 数据
- 不伪装成真实小程序前端

## 用户角色适配

本 MVP 文案和交互默认面向：

- 研究生
- 博士生
- 导师
- 科研助理
- 编辑
- 机构用户

其中最优先的一号用户仍然是：

```text
每天都在处理论文，但不想花太多时间管理系统的中国科研用户。
```

## 反模式清单

以下方向应避免：

- 首页变成复杂文献库
- 页面同时存在多个同级主动作
- 用户必须先配置规则才能开始
- 用户必须理解内部数据结构才能继续
- 输出语义不清，用户分不清草稿和真实发送
- 把导入异常显示成技术错误栈
- 把复杂管理能力直接堆到第一屏

## 设计验收标准

Design 阶段后续稿件若满足以下条件，才算符合本原则：

1. 新用户第一次打开后，30 秒内能理解今天该做什么。
2. 导入流程三步内完成，不需要理解底层格式。
3. 所有渠道输出都显式显示 `draft / preview / not_sent`。
4. 页面主动作清晰，不依赖用户找菜单。
5. 术语更像科研工作流，而不是开发者内部术语。
