Implement Phase 61 only: result share registry saved views admin web shell v1.

Hard boundaries for this phase:
- Do not add source file sharing.
- Do not add local attachment sharing, note-file sharing, or cloud attachment sync.
- Do not add real-time collaboration or live multi-user editing.
- Do not add new delivery channels.
- Do not add desktop or mini UI work in this phase.
- Do not add a generic end-user login/session system.
- Do not add campaign/broadcast/referral behavior.
- Do not add third-party browser analytics scripts.
- Do not add AI attribution, AI summarization, or LLM-based dashboard copy.
- Do not create a new frontend app; extend the existing group-workspace-admin-web only.
- Do not weaken existing auth boundaries.
- Do not replace the modular monolith backend architecture.

Primary goal:
Add local saved-view presets for the already completed read-only result share registry.

This phase should make the repository suitable for:
- saving common share grant registry filters/sorts
- saving common alias registry filters/sorts
- restoring a preferred operator view quickly
- switching between presets without manual re-entry
- staying strictly read-only and file-safe

Architectural intent:
- Reuse existing apps/group-workspace-admin-web only.
- Build on top of the completed Phase 60 registry/filter/sort UX.
- Presets are local-only in v1.
- Presets must never include admin bearer tokens.
- No backend persistence is required unless an extremely small compatibility fix becomes absolutely necessary.

Required changes:

1. Reuse existing app only
Work inside:
- apps/group-workspace-admin-web

Requirements:
- do not create a new frontend app
- preserve current registry/filter/sort/drilldown behavior
- add saved-view UX on top of the existing registry shell

2. Existing admin auth boot flow remains unchanged
Requirements:
- continue in-memory admin bearer token entry
- continue query/fragment token ingestion and immediate URL cleanup
- do not persist admin bearer tokens in:
  - localStorage
  - sessionStorage
  - cookies
- reuse existing API base URL handling

3. Preset persistence boundary
Add local-only preset persistence.

Allowed storage:
- localStorage only for non-sensitive saved-view presets and UI preferences

Must NOT store:
- admin bearer token
- raw share tokens
- raw aliases
- any secret or credential
- any response payloads that exceed compact safe filter/sort state

Suggested storage keys:
- resultShareRegistryGrantPresets
- resultShareRegistryAliasPresets
- resultShareRegistryDefaultPresetId optional

4. Preset models
Add frontend types/view models for:
- ResultShareRegistrySavedView
- ResultShareRegistrySavedViewDraft
- ResultShareRegistrySavedViewSummary
- ResultShareRegistrySavedViewScope = "grant_registry" | "alias_registry"
- ResultShareRegistrySavedViewStoreState

Minimum saved fields:
- id
- name
- scope
- filters
- sort
- createdAt
- updatedAt

Filters/sort should reuse existing safe filter models from Phase 60.

5. Preset actions
Support:
- save current view as preset
- overwrite existing preset
- apply preset
- delete preset
- set default preset optionally
- clear current filters without deleting presets

Requirements:
- presets must be separate for grant registry and alias registry scopes
- applying a preset should update existing filter/sort draft + applied state consistently
- grant ↔ alias quick filter shortcuts from Phase 60 must still work
- preset application must not silently alter unrelated scope state

Extend the existing ResultShareRegistryPanel with:
- saved views section
- save current view action
- preset picker/list
- overwrite action
- delete action
- optional default preset marker

Requirements:
- keep current registry filters and sorts visible
- make it clear presets are local-only
