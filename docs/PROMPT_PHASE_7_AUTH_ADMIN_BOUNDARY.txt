Implement Phase 7 only: authentication and admin boundary v1.

Hard boundaries for this phase:
- Do not add customer-facing end-user login.
- Do not make UserProfile double as an auth identity.
- Do not add multi-tenant or institution features.
- Do not integrate SSO/OAuth/OIDC in this phase.
- Do not add email workflows such as password reset email.
- Do not add frontend work beyond API/OpenAPI responses and docs.
- Do not replace the current modular monolith architecture.

Primary goal:
Introduce a production-friendly auth boundary for internal commercial use:
- human admin authentication
- internal service authentication
- role-based access control
- admin management surface
- audit trail for sensitive actions

This phase should make the backend suitable for:
- protected business/admin APIs
- protected ops APIs
- future admin console integration
- future customer auth separation without refactoring core business entities

Required changes:

1. Separate auth identity from business user profile
Keep UserProfile unchanged as a business/domain entity.
Add separate auth/admin models. Suggested model names are acceptable to refine if needed:
- AdminAccount

- AuditLog

Minimum AdminAccount fields:

- is_active bool

- last_login_at nullable
- created_at
- updated_at

Minimum session/refresh storage:

- admin_account_id fk
- token_hash or refresh_token_hash
- issued_at
- expires_at

- last_used_at nullable
- created_ip nullable

Minimum AuditLog fields:

Use minimal, production-friendly schema changes.
Add Alembic migration(s).

2. Authentication model
Implement two auth modes:

A. Human admin auth
- email + password login
- short-lived access token
- refresh token with server-side revocation support
- logout should revoke the current refresh token/session
- access token should carry admin role and actor identity
- expose /auth/me

B. Internal service auth
- simple bearer token from settings/env
- intended for internal callers such as metrics scraping or future system integrations
- must NOT be allowed to use business CRUD endpoints unless explicitly required below
- allowed for internal ops endpoints and readiness checks

Keep implementation simple and readable.
Do not add external identity providers.

3. RBAC and route protection
Protect the API with clear role boundaries.

Role expectations:
- viewer:
  - read-only business endpoints (GETs)
  - pulse preview
- operator:
  - all viewer permissions
  - business write endpoints
  - pulse run
  - replay/requeue ops actions
  - scheduler tick
- super_admin:
  - all operator permissions
  - admin account management
  - audit log access

Internal service token:
- allowed on:
  - GET /health/ready
  - GET /ops/*
  - POST /ops/scheduler/tick
  - POST /ops/delivery-jobs/{delivery_job_id}/requeue
  - POST /ops/pulse-jobs/{pulse_job_id}/replay
- not allowed on:
  - /users
  - /papers
  - /subscription-policies
  - other business CRUD endpoints

Health behavior:
- GET /health/live remains unauthenticated
- GET /health/ready becomes protected by operator/super_admin or internal service token

4. Auth and admin endpoints
Add at minimum:
- POST /auth/login
- POST /auth/refresh
- POST /auth/logout
- GET /auth/me

Add admin management endpoints under /admin:
- GET /admin/admin-accounts
- POST /admin/admin-accounts
- PATCH /admin/admin-accounts/{admin_account_id}
- POST /admin/admin-accounts/{admin_account_id}/set-password
- GET /admin/audit-logs

Super admin only:
- create admin accounts
- change roles
- deactivate/reactivate admin accounts
- set another admin's password
- read audit logs

For safety:
- prevent deleting the last active super_admin
- prevent self-demotion if it would remove the last active super_admin
- prevent inactive admins from logging in

6. Audit logging
Persist audit records for sensitive events.

At minimum record:
- login success
- login failure
- token refresh
- logout
- admin account create/update/password change
- business write actions on core entities
- pulse run
- scheduler tick
- replay/requeue actions

Audit logging should be lightweight and should not break the request if logging fails unexpectedly; handle that gracefully and document the tradeoff.
