# MVP UI Reference Audit v1

## 目标

Design-1 不写 frontend，不改 backend，只回答一个问题：

```text
面向中国科研用户的 Research Pulse 工作台，界面应该像什么，不应该像什么？
```

本审计的产品铁律是：

> 我们多做一百步，客户少走一步。

这意味着：

- 用户不需要先理解文献管理系统
- 用户不需要先学习导入格式、字段映射、标签体系
- 用户打开产品后，第一眼就应该知道今天该看什么、该处理什么、下一步做什么

## 参考对象总览

| 对象 | 借鉴重点 | 不借鉴部分 | 对 MVP 的结论 |
| --- | --- | --- | --- |
| Zotero | item / collection / tag / attachment / note 的信息模型 | 三栏高密度管理界面、专业用户默认认知负担 | 适合作为数据模型参考，不适合作为首页形态 |
| Paperpile | 简洁列表、搜索、筛选、导入、自动补全、重复提示 | 过强的“人工整理驱动”感觉 | 最接近我们要的文献管理界面方向 |
| ChatGPT / Canvas / Projects | 一个输入框 + 智能工作区、上下文聚合、右侧详情/编辑区 | 通用对话产品的开放式工作流 | 首页与工作台交互理念最值得借鉴 |
| 知网研学 | 覆盖检索、阅读、笔记、成果整理的完整科研场景 | 菜单复杂、路径层级重、功能暴露过多 | 说明中国市场需要完整链路，但要隐藏复杂度 |
| NoteExpress | 中国高校用户对题录管理、全文管理、写作引用的长期需求 | 工具栏密集、传统桌面软件交互负担 | 说明国内用户有强需求，但不意味着界面必须复杂 |
| Elicit | 问题驱动、结构化结果、证据组织 | 强依赖外部检索和 AI 研究助手体验 | 可借鉴“先给问题与结论，再展开资料”的结果组织方式 |

## 逐项审计

### 1. Zotero

#### 界面特点

- 左侧 `collections`
- 中间 `items`
- 右侧 metadata / notes / tags / attachments
- 适合高频文献管理用户长期维护大型资料库

#### 应该借鉴什么

- `item / collection / tag / attachment / note` 的信息模型
- 论文对象与附件、笔记、标签之间的稳定关系
- 论文元数据与阅读笔记分层存放

#### 不应该借鉴什么

- 默认三栏复杂布局
- 让新用户一上来就面对一整套“文献库管理术语”
- 把首页做成论文数据库浏览器

#### 对中国市场的启发

- Zotero 证明了底层模型的成熟性
- 但中国研究生、博士生、导师未必愿意先学会系统，再开始做研究
- 我们应该把复杂结构藏到二级详情里，而不是直接暴露在主界面

#### 结论

```text
Zotero 是底层对象模型参考，不是首页和主工作台参考。
```

### 2. Paperpile

#### 界面特点

- 界面简洁
- 文献列表、搜索、筛选、导入入口都很直接
- 工具栏短，主操作集中
- 自动修复题录、合并重复、规范来源信息的体验更主动

#### 应该借鉴什么

- 顶部主操作集中化
- 左侧轻导航：全部、标签、收藏、过滤器
- 中间列表适合快速扫读
- 让系统自动识别和补全，而不是让用户手动修复每个字段

#### 不应该借鉴什么

- 让“整理文献”变成产品首页的唯一主题
- 过度强调列表管理，而弱化“今天该做什么”

#### 对中国市场的启发

- 最适合借鉴的，不是 Paperpile 的功能数量，而是它的产品态度：
  - simple
  - efficient
  - automatic when possible
- 这与我们的产品铁律高度一致

#### 结论

```text
Paperpile 是文献列表与导入体验的首要界面参考对象。
```

### 3. ChatGPT / Canvas / Projects

#### 界面特点

- 首页极简
- 一个输入框启动工作
- 需要深入处理时，再打开独立工作区或详情区
- 长期任务通过 project/workspace 聚合上下文

#### 应该借鉴什么

- 首页只保留一个核心任务入口
- 把复杂编辑与详情放到侧栏或二级工作区
- 用自然语言作为高级操作入口
- 用上下文聚合替代用户手工找文件夹、找标签、找过滤器

#### 不应该借鉴什么

- 把科研工作台做成纯聊天产品
- 用开放对话替代结构化对象管理

#### 对中国市场的启发

- 用户可以接受极简首页，只要系统足够聪明
- 用户更容易理解：
  - “帮我导入这些论文”
  - “今天我该优先看哪些”
  - “把这几篇标成精读中”

#### 结论

```text
首页体验应更接近 ChatGPT，而不是传统文献库。
```

### 4. 知网研学

#### 界面特点

- 覆盖检索、阅读、摘录、笔记、学习成果创作、多端同步
- 面向中国科研用户的完整场景

#### 应该借鉴什么

- 中国科研场景并不只需要“管理文献”
- 用户关心的是完整科研工作流：
  - 导入
  - 阅读
  - 笔记
  - 摘录
  - 进度
  - 输出

#### 不应该借鉴什么

- 首页承载过多入口
- 把所有子系统一次性铺开

#### 对中国市场的启发

- 国内用户确实需要完整链路
- 但完整链路不等于首页复杂

#### 结论

```text
完整能力要保留在后端和信息架构里，但主界面必须收敛。
```

### 5. NoteExpress

#### 界面特点

- 强调题录、全文、写作引用、参考文献
- 适配高校与论文写作场景

#### 应该借鉴什么

- 写作前后都需要稳定的题录和全文管理
- 国内用户对“引用与写作支撑”有明确预期

#### 不应该借鉴什么

- 传统桌面软件式工具栏堆叠
- 密集菜单与专业术语暴露

#### 对中国市场的启发

- 市场并不排斥专业能力
- 用户排斥的是学习成本和视觉复杂度

#### 结论

```text
能力可以专业，界面不必像传统学术软件。
```

### 6. Elicit

#### 界面特点

- 从研究问题出发
- 输出结构化结论和证据
- 把论文组织成“回答问题的材料”

#### 应该借鉴什么

- 结果组织优先于资料堆叠
- 结构化 sections 比原始列表更适合科研工作推进
- “先给答案，再给材料”适合首页 Research Pulse

#### 不应该借鉴什么

- 当前阶段引入外部检索或外部 LLM 依赖
- 把产品定位成外部学术搜索引擎

#### 对中国市场的启发

- Research Pulse 应该更像“今日科研工作建议”，而不是“今日论文列表”

#### 结论

```text
Elicit 的问题驱动和结构化结果组织值得借鉴，但不应改变当前 deterministic MVP 边界。
```

## 对中国市场的综合启发

### 中国科研用户真正需要的不是“文献库”

更接近以下问题：

1. 今天该看哪几篇？
2. 哪些论文需要我补信息？
3. 哪些论文该推进到精读或已引用？
4. 下一步该做什么？
5. 如何快速生成给导师、课题组或自己复盘的摘要草稿？

### 因此首页不应该是

- 复杂三栏文献库
- 高级检索面板
- 标签/文件夹配置中心
- 导入格式说明页

### 首页应该是

```text
今日 Research Pulse
```

并直接回答：

- 今日重点论文
- 继续阅读与分析
- 下一步动作
- 元数据待补全
- 新导入待筛选

## 对 MVP 产品形态的结论

### 我们应该借鉴

- Zotero 的对象模型
- Paperpile 的简洁文献列表与自动化倾向
- ChatGPT 的极简入口与上下文工作区
- 知网研学 / NoteExpress 的中国科研场景覆盖意识
- Elicit 的结构化结果组织

### 我们不应该借鉴

- Zotero / NoteExpress / 知网研学式高密度首页
- 传统桌面工具栏和功能堆叠
- 先教用户学系统，再让用户做科研
- 任何需要用户先理解内部技术概念的流程

## 最终产品判断

Research Pulse CN 的 UI 方向应定义为：

```text
像 ChatGPT 一样容易开始，
像 Paperpile 一样干净高效，
像 Zotero 一样底层结构稳定，
但比传统文献管理器更主动地告诉用户今天该做什么。
```

## 对后续 Design 阶段的要求

- Design-2 应进一步产出 wireframe spec
- 首页必须围绕 `今日 Research Pulse`
- 导入流程必须压缩为“拖入 -> 预览 -> 确认”
- 论文页必须以“进度”而非“管理”为中心
- 公众号、桌面、小程序都只展示草稿或预览语义
- 所有复杂对象关系只在详情层暴露，不在首页暴露
