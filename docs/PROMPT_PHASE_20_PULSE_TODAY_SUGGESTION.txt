Implement Phase 20 only: pulse today-suggestion card v1.

Hard boundaries for this phase:
- Do not implement any external web/news/paper retrieval.
- Do not implement related-paper or related-news recommendation fetching.
- Do not add AI suggestion generation, AI query generation, or LLM-based advice.
- Do not add new delivery channels.
- Do not add customer-facing UI beyond minimal compatibility needed for existing desktop/digest views.
- Do not sync local file contents, note contents, or review-note contents to the backend.
- Do not add multi-tenant or institution features.
- Do not weaken existing admin auth, internal service auth, device-token sync auth, mini-read auth, or official-account provider boundaries.
- Do not replace the modular monolith backend architecture.

Primary goal:
Add a deterministic "today suggestion" pulse card using only current internal data:
- PaperProfile
- ProgressEvent
- SignalSnapshot
- SubscriptionPolicy / pulse settings context

This phase should make the repository suitable for:
- generating one concise "best next step today" card per user per pulse run
- previewing why this suggestion was chosen
- persisting today-suggestion cards into PulseCard when selected
- including today-suggestion cards in digest/today views without external retrieval

Architectural intent:
- Today suggestion is generated from internal structured data only.
- No AI and no external retrieval are involved.
- It should fit the existing facts -> candidates -> scoring -> suppression -> selection pipeline.
- It should remain explainable and deterministic.
- It should usually point to one paper and one concrete suggestion kind.

Required changes:

1. Extend pulse card model
Add support for a new card type:
- today_suggestion

Requirements:
- update enums / schemas / validators / API response models as needed
- keep schema changes minimal
- if a database migration is required for enum evolution, add the minimal Alembic migration
- source_paper_id should usually be set for today_suggestion when a paper is chosen
- candidate_metadata and score_breakdown must carry enough explanation for ops/debugging

2. Deterministic today suggestion builder service
Add a deterministic service for selecting the best current internal next step for a user.

Requirements:
- input:
  - user_id
  - effective timezone context
- effective timezone resolution order:
  1. explicit request parameter if provided
  2. first enabled daily SubscriptionPolicy policy.timezone if available
  3. app default timezone

Eligible paper set:
- include active papers:
  - in_prep
  - under_review
  - revision
- exclude:
  - paused
- published papers may be considered only if they have both:
  - explicit next_action
  - meaningful recent internal signal context already available
  Keep this conservative and well documented.

Evaluate each eligible paper using only existing internal fields/signals such as:
- type / stage
- priority
- next_action
- blocker
- last_touch_at
- latest progress events if helpful
- latest signal snapshots if helpful and already easy to use cleanly

The builder must produce at most one today_suggestion candidate per user per pulse run.

If no actionable paper exists, do not generate a candidate.

3. Suggestion kinds
Implement deterministic suggestion kinds.

Required supported suggestion kinds in v1:
- execute_next_action
- resolve_blocker
- define_next_action

Behavior:
- execute_next_action:
  - use when next_action exists and blocker is empty
- resolve_blocker:
  - use when blocker exists
- define_next_action:
  - use when paper is active but next_action is empty

The builder must choose one suggestion kind for the selected paper and generate:
- title
- summary
- why_now
- candidate_metadata

All text must be deterministic and concise.
No AI generation.

4. Candidate metadata
today_suggestion candidate_metadata must include at minimum:
- suggestion_kind
- paper_id
- paper_title
- paper_type
- stage
- priority
- next_action nullable
- blocker nullable
- last_touch_at nullable
- days_since_last_touch nullable
- latest_progress_event_at nullable
- latest_signal_snapshot_at nullable
- effective_timezone
- considered_paper_count
- top_reason_codes

top_reason_codes should be deterministic and compact, such as:
- high_priority
- explicit_next_action
- revision_stage
- stale_progress
- blocker_present
- no_next_action_defined

Integrate today_suggestion into scoring and tie-break logic.

- APP_PULSE_MODIFIER_TODAY_SUGGESTION_BLOCKER_PRESENT

Score modifiers should be deterministic and explainable.

Required score_breakdown modifier keys:
- today_suggestion_priority
- today_suggestion_has_next_action
- today_suggestion_revision_stage
- today_suggestion_stale_progress
- today_suggestion_blocker_present

Ordering:

Suggested stable order position:

If implementation chooses a different position, document and test it clearly.

6. Suppression and dedupe
Add safe suppression behavior for today_suggestion.

Requirements:
- respect existing:
  - quiet hours
  - frequency cap
  - low-score suppression
- dedupe should prevent repeating the same today suggestion for the same:
  - user
  - source_paper_id
  - suggestion_kind
  - next_action/blocker summary context when applicable
within the existing dedupe logic/window or a minimal explicit extension if needed

Avoid trivial duplication:
- if practical, suppress today_suggestion when an equal-or-higher-priority paper-centric action card already covers the same paper and same action context in the same run
- if implemented, document the suppression reason clearly
- if not implemented, document as deferred
